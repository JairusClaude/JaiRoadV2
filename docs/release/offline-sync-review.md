# Durable offline reporting — review-only design

Status: review-only server-side text receipt pilot for schema-owner, security and product review. The schema and runtime-grant proposals are not automatic migrations. The backend gate `JAIROADS_MONTHLY_RECEIPTS_ENABLED` defaults false. Improvement1 implements a single encrypted local browser queue with explicit unlock, manual submission, and a receipt-aware lookup. No service worker, automatic background write, or production activation is included. Hosted deployments remain on the approved encrypted portable-draft and single in-page reconnect behavior until the schema and feature gate are separately approved. A period match is not a submission receipt.

## Required transaction and identity contract

- A deliberately queued text-only report receives a cryptographically random UUID. Bind it to the verified canonical account, project, maintenance record, reporting month and canonical payload fingerprint. A receipt must never confer access.
- A server-side receipt table would have a unique (canonical account ID, submission UUID) key and a unique or otherwise constrained reference to the successfully created report, with explicit retention and a schema-owner-approved lifecycle. Store only the minimum required metadata; do not store raw report contents, credentials, paths, or session identifiers in the receipt.
- The server must recompute a versioned fingerprint from validated canonical business fields using deterministic UTF-8 serialization; do not trust a client digest. Define numeric normalization, newline handling, field order and Unicode handling in the protocol. A reused UUID with different content returns conflict without modifying either report.
- In one PostgreSQL transaction: verify the current canonical login and writer scope under the same locking rules as the existing write path; claim the receipt key with unique-constraint conflict handling; create the report under existing reporting-period uniqueness; write its existing audit and notification records; finalize the receipt and commit. Any failure rolls back all of these database changes. No independent transaction may commit the report before its receipt.
- On a repeat, revalidate current authorization and compare the exact canonical fingerprint before returning the recorded outcome. A changed/revoked account, invalid bridge or reassigned record fails closed. A distinct report occupying the same period is a conflict, not success for this request. A lost response is resolved by receipt lookup, not by automatic resubmission.
- Receipt lookup is read-only, authenticated, account-scoped, rate-limited and private/no-store. A missing receipt means unknown at observation, not permission to retry an in-flight write.

## Client lifecycle

1. Save an encrypted text queue only by explicit consent. Improvement1 uses the existing AES-GCM/PBKDF2 envelope with the UUID, account binding, expiry, frozen report and attempted marker inside authenticated encrypted content.
2. Queue a frozen snapshot with explicit expiry. A changed snapshot, expired session, account switch, revocation, or cancellation invalidates queued consent; no silent background action.
3. On reconnection with an active verified session, decrypt only after explicit unlock and check scope. Send one authorized submission. Persist no plaintext report, passphrase, token, or cookie.
4. On network interruption or ambiguous response, present an unknown outcome and a read-only receipt lookup. Only after verified outcome and explicit user action can a new attempt be considered.
5. Browser closure does not submit the queue. The explicitly saved queue remains encrypted in one localStorage slot for later manual unlock and review; no unattended execution occurs. Device eviction, clock changes, shared-device cleanup and retention still require policy review. Never cache private authenticated pages or unrestricted media in a service worker.

## Attachments and activation dependencies

Exclude attachments from the first durable synchronization protocol. Private Storage bytes are outside the PostgreSQL transaction; a later attachment protocol requires separately scoped intents, object identity, quotas, integrity checks, partial-failure recovery, explicit user consent and reconciliation. Do not silently discard selected attachments or replay an uncertain upload.

Before activation, the schema owner must approve table constraints, grants/RLS, migration and rollback, receipt retention, audit/privacy policy and isolated runtime-role rehearsal. Product approval is needed for expiration, conflict UX and background behavior. Run concurrent same-ID/same-payload, same-ID/different-payload, same-period/different-ID, lost-response, rollback after audit failure, revoked account, reassignment, session expiry, cancellation, encrypted-draft tampering and retention tests on a disposable PostgreSQL instance. Hosted staging and human acceptance are mandatory. No production application, DDL or feature flag changes are authorized by this document.

## Implemented review-only server contract

The existing monthly write route accepts an optional UUIDv4 `submission_id` with `reconnect_account_id` and `project_id`. Disabled or missing schema returns 503. The account/key advisory transaction lock is acquired before the existing project/record/authority locks, followed by reauthorization, receipt lookup, duplicate-period validation, report and audit insertion, and atomic receipt insertion. A matching repeat returns the original report ID without another mutation; changed scope or fingerprint returns 409. The fingerprint uses versioned JSON with exact validated decimal spelling and UTF-8 text; differently spelled numeric representations conservatively conflict. A read-only receipt-aware outcome lookup returns `reportId` and `receiptConfirmed` only for the authenticated authorized scope. Retained receipt IDs are deliberately not foreign keys to deletable reports; deleted or moved reports return conflict rather than a new report ID. Non-reuse of canonical IDs and consistent backups/restores including retained receipts are mandatory review conditions. The review-only grant proposal allows runtime SELECT/INSERT; it has not been applied to a hosted database. The ordinary period lookup is unchanged. The opt-in receipt queue sends the UUID only to the receipt-aware lookup and to the write route when the backend gate and schema are available. The independent-connection same-key concurrency regression and receipt transaction tests passed in exact-head focused PostgreSQL workflows on `ff737a522af3cab063783ad678bfc527eeb6a593` ([push](https://github.com/JairusClaude/JaiRoadV2/actions/runs/46021961374), [PR](https://github.com/JairusClaude/JaiRoadV2/actions/runs/46021974750)). These are disposable CI results, not hosted schema or runtime-role acceptance. Hosted schema, RLS/grants and retention approval remain outstanding. No feature is activated in hosted environments.

## Client-side review pilot

One localStorage slot stores only the existing AES-GCM encrypted envelope, containing an account-bound UUID, expiry, text snapshot and attempted marker. Cross-tab Web Locks serialize operations; unavailable locks fail closed. The user must explicitly consent, unlock with the separate passphrase, review the frozen report and choose one send. Receipt and period checks precede the write; the encrypted attempted marker is saved before the POST. No automatic retry or submission after browser closure is implemented. After an attempted write, the queue can only check its receipt or be explicitly removed. The 24-hour send window and one-slot policy still require review, as do device storage eviction, clock behavior, shared devices and manual cleanup. Plaintext is not persisted; attachments are excluded. An ordinary form submission remains separate and the existing server uniqueness and authorization checks remain authoritative. The pilot remains disabled unless the gate is enabled and approved schema exists. The disposable PostgreSQL/browser lifecycle passed on exact head `ff737a522af3cab063783ad678bfc527eeb6a593` in full-system workflows ([push](https://github.com/JairusClaude/JaiRoadV2/actions/runs/46021961304), [PR](https://github.com/JairusClaude/JaiRoadV2/actions/runs/46021974763)). Attachment reconciliation, hosted schema/retention approval and human acceptance remain outstanding.
