## D07 — Supabase auditing replacing custom AuditLog

| Required comparison    | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current dictionary     | One permanent AuditLog business entity with canonical actor, stable snapshot, safe before/after values, transactional successful-change recording and restricted reads. Authentication logging is deferred. No specific replacement is approved.                                                                                                                                                                                                                                                                                                              |
| Current code           | Current business audit writers and notification helper remain. LOGIN listener still writes canonical events; helper creates actor/higher-role recipient rows; some no-op updates audit and many old writers lack full snapshots. These known mismatches are preserved under the Task 1/2 hold; they are not evidence of a completed replacement. Task 2 lifecycle/reassignment adds safe snapshots through the existing writer pattern.                                                                                                                       |
| Current DB             | AuditLog table and two deny-mutation guards exist. No business row-audit insertion trigger was found. pgAudit is **not installed** among five extensions; `pgaudit.log=none`, role empty, row/parameter logging off, no inspected role/database overrides. Existing guards do not capture business changes.                                                                                                                                                                                                                                                   |
| Proposed decision      | Name and approve the replacement mechanism before any cutover. Supabase Auth Audit Logs record **Supabase Auth** events; current Fortify login is not Supabase Auth. pgAudit provides configured SQL/role/object statement evidence, not canonical actor attribution, sanitized row snapshots or application notifications. A reviewed row-change trigger/outbox/history adapter would be another custom mechanism and requires trusted transaction-scoped canonical actor context. Prefer retaining the existing business store until equivalence is proven. |
| Approval required      | Client/team chooses mechanism and accepts any loss of attribution, before/after history, commit-only semantics, access, permanent retention or notifications; schema/security owners approve role/trigger/logging design and retention/costs.                                                                                                                                                                                                                                                                                                                 |
| Affected files/objects | Audit writers in `DdOperationsController`, `DdPhase3Controller`, `DdPeopleLifecycleController`, provisioning/mutation services, Login listener; AuditLog schema/triggers/function, reader models/controllers, dashboard analytics, tests and future logging/actor-context adapter. No `auditLog_behavior` merge or writer/trigger removal is authorized.                                                                                                                                                                                                      |

Mechanism comparison is grounded in current [Auth Audit Logs](https://supabase.com/docs/guides/auth/audit-logs), [pgAudit](https://supabase.com/docs/guides/database/extensions/pgaudit) and [logging configuration](https://supabase.com/docs/guides/observability/configure-logging) documentation. Database connection role is not the person in a Fortify session. CreatedBy/UploadedBy are earlier creator/uploader references and cannot attribute later edits/deletes. Statement logs may include failed/rolled-back attempts; a replacement must prove successful-commit correlation, safe before/after values, retry behavior and pooled-request identity isolation. Do not enable parameter/row logging merely to obtain snapshots: credentials can leak. A retention/export/restore contract must be separately verified rather than assuming platform logs are permanent.

## Additional team decisions

- **ContactNo nullability:** main Engineer field table says nullable, Quick Schema says required. Live and scratch allow NULL; current active creation/edit forms require contact. Confirm whether clearing contact is allowed before changing validation/schema.
- **Quarter date boundaries:** source validates ordinary calendar quarters; Page Specifications PD-05/MR-01 still say boundaries/date semantics unconfirmed. The ten approved policy amendments do not silently settle that separate note.
- **Defaults and identity mode:** confirm dictionary defaults for Account Type/record Status versus explicit application values, and live BY DEFAULT versus scratch ALWAYS identities.
- **Direct authentication cutover:** current integration deliberately preserves Fortify `public.users` plus explicit canonical bridge and synchronized hashes. A future direct UserAccount authenticatable model is a separate architectural implementation, not an approved database reset or a Supabase Auth switch in Task 3.
