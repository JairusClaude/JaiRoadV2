### Confirmed safeguards and gaps

- EngineerLGU composite key, UserAccount EngineerID uniqueness, project RoadCoverage uniqueness and per-record UpdateMonth uniqueness all exist and are validated. All 24 canonical indexes and four Fortify users indexes inspected are valid/ready.
- MaintenanceRecord quarter Q1–Q4, status Ongoing/Completed, positive integer duration, completion-date/state consistency are enforced. There is no mandatory pairing, year-count rule or two-period cap in the database.
- **Missing:** UNIQUE `(project_id,maintenance_year,quarter)` in both live schema and baseline. Aggregate duplicate groups/excess rows = **0/0**, but the table contains **zero rows**. This is an empty-table preflight, not evidence about large/populated data. Recheck immediately before any separately approved execution.
- Application validates StartDate's calendar year/quarter and year range (see `saveRecord`), but DB has no year-range or date-to-year/quarter consistency CHECK. Additive checks are recommendations only; resolve the older Page Specifications calendar-boundary note before changing the logical dictionary on that point.
- Account Type is checked, but active profile/role-link requirements, Admin grandfathering, active LGU assignment and ManagingEngineer eligibility are enforced by Laravel, not by a cross-table CHECK. A blanket non-null EngineerID or role/link CHECK would risk grandfathered Admins. Ordinary CHECK constraints cannot safely implement the full cross-table authorization rule.
- AuditLog recipient/message pairing and self-notification suppression are not DB checks. Current aggregate pairing mismatches = 0; that does not prove event-policy compliance. Action/EntityType also have no closed-vocabulary CHECK while their final vocabulary is pending.
- DB status has no `DEFAULT 'Ongoing'`, and Account Type has no `DEFAULT 'Engineer'`, despite defaults shown in parts of the dictionary/prototypes. Application supplies/validates them explicitly. Confirm intended DB defaults; do not silently add them.

### Audit permanence: installed, not hypothetical

Live `jairoads_next.audit_logs` has two enabled (`tgenabled=O`) triggers:

1. `jairoads_dd_auditlog_reject_changes` — BEFORE UPDATE OR DELETE, row-level.
2. `jairoads_dd_auditlog_reject_truncate` — BEFORE TRUNCATE, statement-level.

Both call `jairoads_next.jairoads_dd_auditlog_deny_mutation()`, a non-SECURITY-DEFINER PL/pgSQL function with `search_path=pg_catalog`, raising SQLSTATE **42501**. These are mutation guards, **not** automatic business-event writers or a Supabase auditing replacement. We did not test mutations against live history. A copied function/trigger definition was verified only in a disposable cluster. Owners/privileged DDL can still disable/drop guards; “append-only” is not immunity from a database administrator. Default origin triggers also require protection against privileged replication-role changes. Preserve both triggers and the function during any migration.

### RLS, grants and private storage

RLS is enabled on all 11 canonical tables, not forced. No policies were found in `jairoads_next`, `public` or `storage`. Among inspected API roles, `anon`, `authenticated` and `service_role` have **no USAGE on `jairoads_next`** and no canonical table grants; owner `postgres` has canonical table privileges. `postgres` and `service_role` have BYPASSRLS; anon/authenticated do not. This currently denies ordinary API access to canonical tables rather than providing per-account JWT policies. Laravel authorization remains necessary for a privileged PDO connection. The deployed application's actual DB credential/role and Data API exposed-schema settings were not inspected; do not infer them solely from the catalog or add `auth.uid()` policies to a Fortify bigint identity system.

Both `jairoads-maintenance-documents` and `jairoads-monthly-media` have `public=false`. Neither has a bucket-specific size limit. Documents have no bucket MIME allowlist; media allowlist matches DB/application's JPEG/PNG/WebP/MP4/WebM set. This does **not** prove unlimited uploads: project/global Storage limits were not inspected. No Storage objects, signed links or bytes were fetched. Current server-side storage services use private paths and server-only credentials; bucket privacy does not replace parent-record authorization.
