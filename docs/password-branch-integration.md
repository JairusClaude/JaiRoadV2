## Security and preserved behavior

The updater locks the persisted Fortify user first, then its explicit DD account; DD Settings uses the same order when changing a password. There is no email/numeric-ID inference. It checks persisted account/link/email/active status and any linked Engineer profile. Password changes require the current credential and matching existing hashes; only broker-token-verified reset can repair old desynchronization. One hash is generated and saved to both tables within one transaction. Credential SQL errors become a generic validation response without chaining/reporting SQL bindings. The authenticated model is synchronized only after the enclosing transaction commits, so audit failures roll back hashes, username and remember token without leaving a changed in-memory principal.

Remember tokens rotate and applicable database sessions are revoked for the changed account. AuthenticateSession rejects stale password-hash sessions for all supported session stores. Login-time rehashing updates both linked hashes rather than disabling configured upgrades. The additional provider check rejects inactive/email-mismatched/hash-mismatched/retired linked identities before ordinary credential authentication, including when rehashing is unnecessary.

Existing unlinked Admin compatibility and new Admin/Engineer profile requirements remain unchanged. Viewer restrictions, active EngineerLGU scope, ManagingEngineer selection/self-management, immutable ordinary-edit manager/period fields and unrestricted available Q1–Q4 choices are preserved. Public registration stays disabled. The legacy-only provider/reset/settings path remains supported. No password, hash, reset token, MFA secret or passkey material is added to audit payloads.

Existing AuditLog writers, notification policy, LOGIN audit listener and history are retained. `auditLog_behavior` is not merged. No canonical/legacy model, migration, production constraint/index/trigger, storage service or real account is changed. The tested append-only SQL never reaches shared Supabase. The current Fortify User infrastructure plus explicit DD link is preserved; this is not a direct UserAccount authentication cutover.
