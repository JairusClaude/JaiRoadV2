# Repair B — approved NULL relationships and preserved history

4 November 2026. This new team-approved policy supersedes older blanket restrictive-deletion assumptions **only** for MaintenanceRecord's current project and manager relationships. See the [18-FK dependency matrix](dependency-matrix.md), prepared from a read-only live inspection before implementation. No official Google Doc was edited; the amendment below is ready for review/application by the documentation owner.

## Ready-to-apply Data Dictionary amendment

- `MaintenanceRecord.ProjectID` may be SQL NULL only for retained project history with protected historical context. Creating a new MaintenanceRecord still requires an existing authorized MaintenanceProject. Deleting one MaintenanceProject explicitly detaches its records; it never deletes MaintenanceRecords, MonthlyUpdates, MaintenanceDocuments, Media, private objects, the RoadCoverage, identities or historical AuditLogs.
- Preserve a distinct immutable snapshot of the former project (including creator and timestamps), road identifier/name and LGU identifier/municipality/province/region. The current ProjectID is NULL, never the deleted ID or a placeholder project. Historical context must be labelled separately from a current active link.
- Detached history is read-only and accessible only to active canonical Admin/SuperAdmin accounts through dedicated historical views/downloads. Engineer/Viewer scope is never inferred from a NULL project or historical snapshot. Future reassociation, orphan editing or non-administrator historical permissions need a separately approved workflow.
- `MaintenanceRecord.ManagingEngineerID` may be SQL NULL after an explicit administrator unassignment. New records still require an eligible active manager. NULL gives no Engineer editing rights. An eligible replacement is explicitly assigned through the existing reassignment workflow; direct old-to-new changes are atomic and do not introduce an artificial intermediate NULL.
- Only Admin/SuperAdmin may delete or change assignments. An Engineer can edit only as current eligible ManagingEngineer, with active canonical account/profile and active LGU assignment. Viewer remains read-only. Normal record editing cannot change project/manager; it may preserve a pre-existing NULL manager.
- Accounts and Engineer profiles are retained/deactivated/retired, not hard-deleted to clear provenance. `created_by`, `uploaded_by`, AuditLog `user_id`, historical ActorIdentifier and historical OldValue/NewValue remain untouched.
- All other relationship nullability and all existing foreign-key delete actions remain unchanged. Referenced parent deletion stays blocked where no approved detachment/history design exists. Optional UserAccount EngineerID and AuditLog RecipientUserID retain existing semantics.

## Application operation and concurrency

`PreservedProjectDeletion` generates a current server-side impact preview containing project ID/title, road association and all four dependent counts, including zeros. The canonical confirmation pane states that related records/files will be preserved and current project references become NULL. Cancel has no mutation. Only one project is supported per confirmation; bulk controls remain disabled.

The preview is encrypted/authenticated, bound to the canonical actor/project, expires after 15 minutes and includes a SHA-256 fingerprint of the full current project/road/LGU/record/update/document/media state. A final request supplies the token, never a trusted child list. Both the new canonical DELETE route and the existing DD generic project-delete route require that preview. Missing/tampered/wrong-actor/expired/stale confirmations cannot bypass it.

Final deletion locks in road -> project -> record -> update/document/media order, matching municipality/project/maintenance writes. Parent FOR UPDATE locks prevent unnoticed FK child inserts; child locks prevent concurrent material edits. Current canonical actor/profile and application lifecycle locks protect revocation, and authorization is resolved again after lock waits. Snapshot insertion, project_id NULL updates, selected project deletion and one new audit entry commit atomically. A database/audit failure rolls all of them back. Transaction retries cannot leave duplicate committed events. No Storage method is called by this operation.

Unassignment is a separate labelled Admin action with confirmation and expected-current-manager validation. NULL is explicit and distinct from a missing field, zero or an empty-string ID. The existing reassignment operation accepts an explicitly expected NULL, validates replacement account/profile/LGU eligibility and preserves original creators. A stale expected manager fails. New unassignment and project deletion use the current AuditLog format without new notification fan-out. Existing reassignment notification behavior is retained; no AuditLog architecture is replaced.

Document metadata editing now follows parent -> record -> file lock order and checks live authorization after waiting, preventing edits using permission from before project detachment/unassignment. Monthly creation/editing and uploads already take parent locks and revalidate. Individual file deletion remains Repair A's independent, separately confirmed operation; it can resolve an Admin-authorized detached record through protected context.

## Readers, NULL display and historical access

The integrated linked-record directory/project history uses LEFT JOIN only for the nullable current manager. The required current project/road/LGU joins remain intact. Manager DTOs are actual JSON NULL, and all active linked record/history/legacy DD presentations show `NULL (unassigned)`. Canonical forms preserve a pre-existing NULL without converting it to ID 0; new-record validation still rejects missing project/manager. Existing canonical read-only Eloquent belongsTo relationships return null naturally; their fields/keys/relationships were not edited.

Detached records are deliberately excluded from ordinary project-based directories, project/period selectors and normal activity-edit routes. Admin/SuperAdmin use `/dd-phase3/history/records` and `/dd-phase3/history/records/{id}` with bounded independent pagination for records, MonthlyUpdates, documents and media. The current Project field shows `NULL (Project deleted)`; previous project/road/LGU are clearly labelled historical snapshots, with no active link to the deleted project. Snapshot data never grants authorization. Original creator/uploader references and private download access remain available to administrators. Engineer/Viewer direct historical/download requests fail; no private paths are projected.

Admin dashboard totals include retained records/reports/files and link to the historical view. Engineer totals stay restricted to current managed work in active LGUs. Viewer analytics/inventory totals now exclude detached records and their reports/documents, matching the Admin-only historical policy. This does not broaden Viewer access to any data.

## Schema-owner handoff — not executed on shared infrastructure

The forward-only anonymous migration proposal is `database/proposals/preserve_project_history.php`, outside automatic migration directories. Existing teammate-owned migrations/models and shared Supabase were not changed. Shared activation requires separate schema-owner review/application; application preview/deletion/unassignment stay unavailable until the proposal's table and both nullable columns are present. Existing non-NULL reassignment and ordinary workflows remain compatible before activation.

Proposed atomic sequence:

1. On a reviewed staging/disposable copy, inspect actual field nullability/FKs, verify no unexpected orphans or duplicate context table, establish the trusted Laravel backend role, and coordinate application release. Keep all 18 existing RESTRICT FKs and existing indexes/uniqueness rules.
2. In one transaction create private `jairoads_next.maintenance_record_contexts`: per-record primary key/FK RESTRICT, historical former-project ID (intentionally no FK to the deleted row), immutable JSON snapshot, canonical detaching actor FK RESTRICT and timestamp. Enable RLS, revoke PUBLIC/anon/authenticated access; grant only the reviewed backend role needed for INSERT/SELECT. No browser/Data API policy is added. GRANT alone does not bypass RLS: the backend must use its reviewed owner/BYPASSRLS role, or the schema owner must separately approve narrowly scoped backend-only policies. Verify this with the actual runtime role, not just the schema owner.
3. Install new-table append-only UPDATE/DELETE/TRUNCATE protections and revoke PUBLIC function execution. Preserve completed context indefinitely unless an explicitly reviewed retention plan replaces this policy.
4. Drop NOT NULL only on `maintenance_records.project_id` and `maintenance_records.managing_engineer_id`. Do not change their FK definitions. Add a deferred constraint trigger requiring a persisted context before a NULL project can commit. Application inserts context and detaches in the same transaction; an arbitrary orphan without context fails at commit. No unrelated FK is loosened and no SET NULL cascade is introduced.
5. Rehearse application operations, historical reads, direct authorization, concurrency, failure rollback, constraints/RLS/grants and unchanged normal creation. The proposal's `down()` intentionally refuses destructive rollback; do not set NOT NULL back over retained NULL rows or drop contexts.
6. Obtain schema-owner execution approval separately. After coordinated activation verify checks read-only, then use only independently authorized test/acceptance data. This coding task does not authorize shared schema or live data writes.

Repair A's `file_deletions` proposal is independent: it is needed for explicit individual file deletion/recovery, not for preserving Storage objects during project deletion. Neither proposal runs at container startup, through a request, or via the default migrations. Guarded disposable browser/Docker fixtures explicitly rehearse both only on fresh local PostgreSQL 17.

## Remaining deliberately unsupported cases

No blanket nullification of LGU/RoadCoverage/MonthlyUpdate/file-parent links, account/Engineer hard deletion, orphan Engineer/Viewer access, automatic project replacement, placeholder projects, bulk project deletion, detached-record editing or reassociation is implemented. Their restrictive constraints/absence of endpoints preserve data. Project deletion does not cancel or falsely complete an already accepted independent Repair A deletion intent; those commands retain their existing verified recovery semantics. Storage bytes already removed by such a separately confirmed command are not recreated.

Database/table owners can administer or disable protections outside the application; app authorization and these triggers are not a substitute for database role governance. The schema owner must verify actual trusted-role grants/RLS and deployment order before activation. Historical creator IDs embedded in snapshots continue to depend on the approved account-retention policy; no UserAccount hard-delete workflow is introduced.
