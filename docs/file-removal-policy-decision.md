# MaintenanceDocument and Media retention decision

> Historical checkpoint. On 4 November 2026 the team approved permanent deletion of one selected MaintenanceDocument or Media, including its exact private object. See [the approved implementation and operational handoff](permanent-individual-file-deletion.md). The older undecided text below is retained as history, not current individual-deletion policy. Shared activation remains gated by schema-owner setup. Parent/bulk/cascade deletion is not approved by this decision.

Deletion is NOT enabled. Admin/SuperAdmin may open a non-mutating, parent-authorized deletion review. Engineers/Viewers cannot access that review. There is no document/media DELETE route and no storage deletion call. Existing downloads/uploads/private buckets are unchanged. Preparing a review does not write an AuditLog successful-change event.

Team/client and the storage/schema owners must choose one behavior before destructive endpoints can be implemented:

| Alternative                                                        | Consequences and approvals needed                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Remove the database record, retain its private object              | Preserves recoverable bytes, but leaves an unreferenced object. Approve retention duration, authorized retrieval/recovery, inventory ownership and later cleanup. Current downloads resolve database metadata, so retained bytes alone do not preserve a user-visible download.                                                                                |
| Remove metadata and permanently purge the object                   | Irreversible byte loss; PostgreSQL and HTTP Storage cannot commit atomically. Approve a durable retry/compensation strategy, recovery expectations, success/failure definitions and audit retention before implementation. Deleting bytes before a failed SQL commit or deleting metadata before failed Storage cleanup must not be presented as full success. |
| Retain metadata with an archived/retention state, then purge later | Needs a separately reviewed schema/workflow/retention design. No such columns, tables, background jobs or lifecycle states are introduced here.                                                                                                                                                                                                                |

Also confirm restrictive dependencies, private-object retention while related business history remains, filename/path confidentiality, administrator confirmation wording and before/after audit payload. Do not reinterpret upload-failure compensation (`removeAfterFailure`) as an approved user deletion policy. It remains limited to compensating a failed new upload.

A selected option is a policy decision, not authorization to alter shared buckets or records. Rehearse approved database and storage failure cases in isolated infrastructure before live execution. This task uses only non-destructive review and storage mocks; no live object is changed.
